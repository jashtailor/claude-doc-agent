# claude-doc-agent

A small agent that answers questions about a folder of documents. You point
it at contracts, invoices, and memos, ask it something in plain English, and
it searches the documents, pulls out the specific fields it needs, and
writes you an answer that names the document it got the answer from.

It is a teaching-size demo, not production software. The goal was to build
the whole loop end to end (tool use, a system prompt, a retrieval step, a
CLI) in a way that is small enough to read in one sitting and runs with zero
setup, since it ships with a mock mode that needs no API key at all.

## Quickstart

```bash
git clone https://github.com/jashtailor/claude-doc-agent.git
cd claude-doc-agent
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# No API key needed:
python agent.py --mock "What is the amount due on the Harborview invoice?"

# With a real key, drop --mock:
export ANTHROPIC_API_KEY=sk-ant-...
python agent.py "What is the amount due on the Harborview invoice?"
```

Leave off the question entirely and either mode drops into an interactive
loop where you can keep asking things until you type `quit`.

The `documents/` folder already has ten synthetic files in it (three
contracts, four invoices, three internal memos), generated by
`generate_documents.py`. Rerun that script if you want to regenerate them or
add your own.

## The two tools

The agent gets exactly two tools, on purpose:

- **`search_docs(query)`** does plain keyword search over every document
  and returns the top few matches with a relevance score and a snippet.
  This is the "where do I even look" step.
- **`extract_field(document, field)`** goes into one document's header
  block (every document starts with a few `Key: Value` lines like `Amount
  Due` or `Effective Date`) and pulls out the value for a named field,
  matching loosely so "amount" still finds "Amount Due."

Two tools instead of one general "read this document" tool because the
split forces two different failure modes to be visible. If search comes
back with the wrong document, you see that in the transcript before the
model ever tries to extract anything. If extraction pulls the wrong field,
you see that separately. A single do-everything tool would hide both of
those behind one opaque call.

I picked keyword search over embeddings for the same reason. Ten documents
do not need a vector index, and a demo about tool use should not spend its
complexity budget on retrieval infrastructure. The tradeoff is real: plain
keyword counting has no notion of relevance beyond "this word showed up."
Ask it "who are the parties in CTR-2031" and it will sometimes rank a memo
that happens to mention CTR-2031 twice above the actual contract, because
the memo's raw keyword count is higher. A real system would use embeddings,
or at least weight the document's own ID field higher than incidental
mentions. This one does not, and that is a deliberate line to make the
retrieval step's limits visible rather than paper over them with a fancier
index that would obscure what a two-tool agent loop actually looks like.

## How the system prompt is structured

The system prompt does three things and nothing else: names the two tools
and when to reach for each one, tells the model to use `search_docs` before
`extract_field` (you need to know which document before you can pull a
field from it), and tells it to cite the filename it got an answer from and
say plainly when the tools come up empty instead of guessing. That last
part matters more than it sounds. Without it, a model asked about a
document that is not in the folder will happily invent a plausible-looking
answer instead of saying "I don't see that document."

## Where it fails

Being upfront about the rough edges:

- **Keyword search has no ranking beyond raw counts.** Covered above. It
  favors whichever document repeats the query's words most often, not
  whichever document a human would call most relevant.
- **`extract_field` only looks at the header block.** Anything mentioned
  in a document's prose body (a dollar figure or date buried in a
  paragraph) is invisible to it. That is a real limitation, not a bug. The
  header is a small, first-class table on every synthetic document, and
  extraction only knows how to read tables.
- **The mock model is rule-based, not a language model.** It runs the same
  two tools as the real agent, but the "reasoning" is a couple of
  if-statements (does the question look like it wants one field, or is it
  open-ended). That is enough to demo the loop and keep tests fast and
  offline, but it will misfire on anything that does not fit its two
  patterns. The real Claude-backed mode does not have this limitation.
- **No memory across questions.** Every call to `agent.py "..."` starts a
  fresh conversation. The interactive REPL mode also resets between
  questions rather than carrying context forward, since that would need
  its own design (when to forget, how much history to keep) that felt out
  of scope for a two-tool demo.

## Example session

```
$ python agent.py --mock "What is the amount due on the Harborview invoice?"
According to invoice_10432.txt, Amount Due is $12,340.00.

$ python agent.py --mock "What is the total contract value for CTR-2059?"
According to contract_summit_ridge_lease.txt, Total Contract Value is $412,800.00.

$ python agent.py --mock "What does the loading dock safety memo say?"
Here's what I found across the documents: - memo_safety_protocol.txt: Document
Type: Internal Memo Memo ID: MEMO-0087 Date: 2024-05-02 From: Priya Sharma,
Operation... - memo_vendor_review.txt: Document Type: Internal Memo Memo ID:
MEMO-0093 Date: 2024-06-20 From: David Okafor, Procureme... - memo_lease_renewal.txt:
Document Type: Internal Memo Memo ID: MEMO-0101 Date: 2024-08-05 From: Lena
Ostrowski, Facilit...
```

That third one is the keyword-search limitation from above in action: the
question is open-ended enough that no single `extract_field` call applies,
so the agent falls back to listing the top matching documents with a
snippet from each, safety memo first, which is the useful one, but the
other two memos tag along since they also mention loading-dock-adjacent
words.

Here is what the same first question looks like against the real API
(shortened; the real run streams token by token):

```
$ python agent.py "What is the amount due on the Harborview invoice?"
Let me look that up.
[tool call: search_docs(query="Harborview invoice amount due")]
[tool result: invoice_10432.txt, score 4, "...Bill To: Harborview Dental Group..."]
[tool call: extract_field(document="invoice_10432.txt", field="amount due")]
[tool result: {"document": "invoice_10432.txt", "field": "Amount Due", "value": "$12,340.00"}]

According to invoice_10432.txt, the amount due is $12,340.00.
```

## Running the tests

```bash
pip install -r requirements.txt
python -m pytest
```

The tests only exercise the tools and the mock loop, so they run offline
and do not touch the API or cost anything.

## Project layout

```
agent.py               CLI entry point: the conversation loop, real and mock
doc_tools.py            search_docs and extract_field, shared by both modes
generate_documents.py    writes the synthetic documents/ folder
documents/               ten generated contracts, invoices, and memos
tests/                   tests for the tools and the mock loop
```
